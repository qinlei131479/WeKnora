# 匹配与时效规则

先登记数据源，再逐项匹配。输出用词以 `output-spec.md` 为准。

## 1. 数据源登记

每个任务只使用已登记的真实源文件。按文件性质分成三类：

| 性质 | 用途 | 必须有 |
| --- | --- | --- |
| 标准清单 | 判断标准能力是否可复用 | 一级/二级/三级功能、功能描述、是否最小销售单元、依赖模块 |
| 历史工时清单 | 提供可比历史时效 | 功能描述和产品、研发、交付时效 |
| 需求清单 | 提供本次待评估能力 | 功能层级和核心功能描述；可另含状态、批注、人工标注 |

登记每份源文件时记录：

```text
文件名、知识库名（如有）、Sheet、字段映射、有效行范围、合计行/说明行排除规则、文件 hash（可计算时）
```

不要假设固定文件名、Sheet 名或业务领域。不要只信表格维度元数据；必须按实际行读取，并保留行号。

## 2. 检索顺序

对每条报价行先拆能力项，再按顺序判断：

```text
核心功能描述 + 能力项矩阵
    │
    ├─ 标准行覆盖全部必做能力项        → P1 已匹配；仅标准命中时时效为 0
    ├─ 标准行只覆盖部分必做能力项      → P1 部分匹配，缺口走 P2/P3
    ├─ 标准无该单元，历史有可比行/组合 → P2
    └─ 两库都无可复用源行             → P3 未匹配
```

匹配键是「角色 + 操作 + 业务对象 + 目标」。标题、模块名或关键词相似不构成匹配证据。

检索时先产出候选行，再判断。候选行必须保留：

```text
源ID = 文件名 + Sheet + 行号
命中原文 = 源表功能描述原文
覆盖判断 = 覆盖哪些能力项 / 缺哪些能力项
```

## 3. 最小销售单元

标准清单中，下面两列值为「是」的行才是可独立报价单元：

- 二级功能是否为最小销售单元
- 三级功能是否为最小销售单元

常见同义表头按字段含义映射。空值、合并单元格向下填充后再判断。

取值规则：

- `是`：可独立销售。
- `-`、`无`、空：附属能力，并入其依赖的最小销售单元，除非用户把它写成独立需求。
- `/` 视为无效三级名时，回退用二级功能名。

## 4. P1：标准产品

已匹配必须同时满足：

1. 命中的是标准清单中的最小销售单元或其明确附属能力。
2. 该行原文覆盖全部必做能力项。
3. 主路径界面、数据模型或流程可直接复用。

部分匹配必须写清：

```text
标准系统 {功能} 已支持 {已有能力}，但未覆盖 {缺口}，需 {改造动作}。
```

### 4.1 标准时效规则

标准清单只作能力依据。仅命中标准功能清单时：

1. 产品时效 = `0`。
2. 研发时效 = `0`。
3. 交付时效 = `0`。
4. 「工时说明」逐列写明：0 来自哪个标准功能行；格式必须符合 `output-spec.md`。

标准清单中的时效列、经验数或参考值都不进入报价结果。若需要非零工时，必须找到可比历史行；找不到时按 P3 拆缺口。

## 5. P2：历史项目

历史文件必须确认可作时效依据。没有产品、研发、交付三个时效值的需求清单或项目功能清单，不能作为 P2 时效来源。

取数规则：

| 场景 | 规则 |
| --- | --- |
| 单行可比 | 直读该行产品、研发、交付，不改数 |
| 一个报价行覆盖多条历史原子任务 | 先确定参与行，再三列分别求和 |
| 历史行是合计行或说明行 | 排除，不参与计算 |

每条 P2 时效必须记录所有参与行：

```text
研发=12：历史功能「直播监测」5（{历史文件名}，Sheet：{Sheet}，行：10） + 历史功能「点播监测」4（{历史文件名}，Sheet：{Sheet}，行：11） + AI原子任务「采集适配」3（AI评估，L2，需新增红外/HDMI采集适配）
```

不能只写历史文件名，不能修改历史行数值，也不能用项目总工时、模块总工时或平均值反拆。

## 6. P3：AI 评估

只在标准和历史都无源行，或部分匹配的缺口没有可比历史行时使用。仅标准命中不需要 P3 补工时，因为它按规则为 0。

真实未匹配行必须固定为：

- 功能匹配结果：`未匹配`
- 匹配模块：`-`
- 匹配依据：`未从标准产品功能清单和历史项目库中找到匹配项`
- 匹配来源：`AI评估（原子任务拆解）`

部分匹配的缺口走 P3 时，功能匹配结果仍写「部分匹配」；工时说明仍按产品、研发、交付逐列写，并在每列中区分可追溯底座项和缺口任务项，来源必须写清标准能力来源和「时效：AI评估（缺口原子任务拆解）」。

P3 工时按 `ai-estimation.md` 拆原子任务，并在「工时说明」保留每个任务名、数值、定级和原因。拆不出原子任务，或不能说明某列为什么是这个数时，该列填 `--`。

## 7. 部分匹配加总

部分匹配 = 可复用底座时效 + 缺口时效。

- 底座：仅标准命中按 0，或有历史可比行时按 P2 直读。
- 缺口：P2 可比改造行，或 P3 原子任务。
- 两段相加，不加风险系数、改造系数或管理预留。

依据必须同时出现「已有」和「未覆盖/需新增」。没有可追溯底座时，整行按未匹配处理。

部分匹配允许某一列可追溯、另一列不可追溯：可追溯列写取数式，不可追溯列写 `--`；不得为了表面完整给另一列拍数。

## 8. 依赖模块

依赖字段只取标准清单中的：

- 二级功能依赖模块
- 三级功能依赖模块

忽略空、`-`、`无`、`无（核心基础模块）`。多个依赖按顿号或逗号拆开、去重后各出一行。

依赖行规则：

1. 三级功能名末尾直接加 `*`，无空格。
2. 时效取该依赖模块作为最小销售单元时的时效；取不到则按 P1 → P2 → P3 降级。
3. 依赖行必须有独立证据和独立时效依据。
4. 同一依赖被多个主功能引用时，每个主功能下各出一行；在摘要提示重复出现，不自行省略。

## 9. 禁止事项

- 只凭功能名相似写匹配。
- 用高层架构、基础平台、通用组件兜底真实功能。
- 引用不存在、未登记或未打开过的文件。
- 把需求清单、项目功能清单当成历史工时清单。
- 只写文件名，不写 Sheet 和行号。
- 用项目总工时或模块总工时摊到无关功能。
- 修改历史行数值，或用平均值代替直读/累加。
- 在 P1/P2/P3 上乘任何系数。
- 用“框架可复用”“方法论需新增”等定性结论代替逐列数字推导。
