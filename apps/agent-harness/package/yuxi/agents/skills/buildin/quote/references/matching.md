# 匹配与时效规则

先登记数据源，再逐项匹配。输出用词以 `output-spec.md` 为准。

## 1. 数据源登记

每个任务只使用已登记的真实源文件。按文件性质分成三类：

| 性质 | 用途 | 必须有 |
| --- | --- | --- |
| 标准清单 | 判断标准能力是否可复用并提供标准时效 | 一级/二级/三级功能、功能描述、是否最小销售单元、依赖模块；时效列有则登记 |
| 历史工时清单 | 提供可比历史时效 | 功能描述和产品、研发、交付时效 |
| 需求清单 | 提供本次待评估能力 | 功能层级和核心功能描述；可另含状态、批注、人工标注 |

登记每份源文件时记录：

```text
文件名、知识库名（如有）、Sheet、字段映射、有效行范围、合计行/说明行排除规则、文件 hash（可计算时）
```

不要假设固定文件名、Sheet 名或业务领域。不要只信表格维度元数据；必须按实际行读取，并保留行号。

## 2. 检索顺序

对每条报价行先拆能力项，再按顺序判断：

```text
核心功能描述 + 能力项矩阵
    │
    ├─ 标准行覆盖全部必做能力项        → P1 已匹配；直读标准行三列时效
    ├─ 标准或历史只覆盖部分能力项      → 拆成「已匹配」行 + 「未匹配」行
    ├─ 标准无该单元，历史有可比行/组合 → P2
    └─ 两库都无可复用源行             → P3 未匹配
```

匹配键是「角色 + 操作 + 业务对象 + 目标」。标题、模块名或关键词相似不构成匹配证据。

检索时先产出候选行，再判断。候选行必须保留：

```text
源ID = 文件名 + Sheet + 行号
命中原文 = 源表功能描述原文
覆盖判断 = 覆盖哪些能力项 / 缺哪些能力项
```

## 3. 最小销售单元

标准清单中，下面两列值为「是」的行才是可独立报价单元：

- 二级功能是否为最小销售单元
- 三级功能是否为最小销售单元

常见同义表头按字段含义映射。空值、合并单元格向下填充后再判断。

取值规则：

- `是`：可独立销售。
- `-`、`无`、空：附属能力，并入其依赖的最小销售单元，除非用户把它写成独立需求。
- `/` 视为无效三级名时，回退用二级功能名。

## 4. P1：标准产品

已匹配必须同时满足：

1. 命中的是标准清单中的最小销售单元或其明确附属能力。
2. 该行原文覆盖全部必做能力项。
3. 主路径界面、数据模型或流程可直接复用。

只能覆盖部分必做能力项时，不得输出「部分匹配」。先记录覆盖判断，再把原需求拆成两条：

```text
已匹配行：{标准或历史功能}已支持{已有能力}，按源行时效取数。
未匹配行：{缺口能力}未覆盖，需{改造动作}，按 P3 拆解。
```

两条相邻行的一级、二级功能一致，三级功能分别表达被覆盖能力和缺口能力，并使用同一个 `merge_group`。

### 4.1 标准时效规则

标准行自身时效是 P1 时效来源：

1. 该行「产品」「研发」「交付」三项都有数值时，逐项直读，不改数。
2. 三项都没有数值，或源表没有这三列时，产品、研发、交付都按规则 `0`。
3. 只有部分项有数值时，有值项直读；缺失项填 `--`，不从合计、比例或其他列推测。
4. 「工时说明」逐列写明每个数值来自哪个标准功能行；格式必须符合 `output-spec.md`。

标准或历史源行数值不得与 P3 拆解值混在同一个最终匹配行里；部分覆盖必须拆行后分别取数。

## 5. P2：历史项目

历史文件必须确认可作时效依据。没有产品、研发、交付三个时效值的需求清单或项目功能清单，不能作为 P2 时效来源。

取数规则：

| 场景 | 规则 |
| --- | --- |
| 单行可比 | 直读该行产品、研发、交付，不改数 |
| 一个报价行覆盖多条历史原子任务 | 先确定参与行，再三列分别求和 |
| 历史行是合计行或说明行 | 排除，不参与计算 |

每条 P2 时效必须记录所有参与行：

```text
研发=9：历史功能「直播监测」5（{历史文件名}，Sheet：{Sheet}，行：10） + 历史功能「点播监测」4（{历史文件名}，Sheet：{Sheet}，行：11）
```

不能只写历史文件名，不能修改历史行数值，也不能用项目总工时、模块总工时或平均值反拆。

## 6. P3：AI 评估

只在标准和历史都无源行，或拆分后的缺口没有可比历史源行时使用。

真实未匹配行必须固定为：

- 功能匹配结果：`未匹配`
- 匹配模块：`-`
- 匹配依据：`未从标准产品功能清单和历史项目库中找到匹配项`
- 匹配来源：`AI评估（原子任务拆解）`

拆分后的缺口单独成行，功能匹配结果写「未匹配」；工时说明逐列列出 P3 原子任务，匹配来源写「AI评估（原子任务拆解）」。

P3 工时按 `ai-estimation.md` 拆原子任务，并在「工时说明」保留每个任务名、数值、定级和原因。拆不出原子任务，或不能说明某列为什么是这个数时，该列填 `--`。

## 7. 拆分行加总

原需求总时效 = 已匹配行时效 + 未匹配行时效。

- 已匹配行：标准行直读，或历史行直读/累加。
- 未匹配行：P3 原子任务求和。
- 两行各自保留完整工时说明；不把两行数字合并回一行。
- 两行一级、二级功能一致且相邻，JSON 使用同一个 `merge_group`。

没有可追溯底座时，不需要拆分，整行按未匹配处理。

## 8. 依赖模块

依赖字段只取标准清单中的：

- 二级功能依赖模块
- 三级功能依赖模块

忽略空、`-`、`无`、`无（核心基础模块）`。多个依赖按顿号或逗号拆开、去重后各出一行。

依赖行规则：

1. 三级功能名末尾直接加 `*`，无空格。
2. 时效取该依赖模块作为最小销售单元时的时效；取不到则按 P1 → P2 → P3 降级。
3. 依赖行必须有独立证据和独立时效依据。
4. 同一依赖被多个主功能引用时，每个主功能下各出一行；在摘要提示重复出现，不自行省略。

## 9. 禁止事项

- 只凭功能名相似写匹配。
- 用高层架构、基础平台、通用组件兜底真实功能。
- 引用不存在、未登记或未打开过的文件。
- 把需求清单、项目功能清单当成历史工时清单。
- 只写文件名，不写 Sheet 和行号。
- 用项目总工时或模块总工时摊到无关功能。
- 修改历史行数值，或用平均值代替直读/累加。
- 在 P1/P2/P3 上乘任何系数。
- 用“框架可复用”“方法论需新增”等定性结论代替逐列数字推导。
