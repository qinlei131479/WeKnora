# 报价技能书

基于本次任务登记的权威数据评估工时，按模板导出可追溯报价单。技能不预设清单文件名；标准产品、历史项目和需求清单都由用户上传或从知识库动态获取。

细则按需读取：

- 匹配与时效规则：`references/matching.md`
- 数据源登记与字段契约：`references/data-index.md`
- 输出模板与金样：`references/output-spec.md`
- P3 拆解估时：`references/ai-estimation.md`

## 硬约束

1. 本阶段只输出工时，不输出单价、税率和金额。
2. 命中本技能后，先建立输入清单并读取全部上传附件；附件读取和解析完成前，禁止拆需求、匹配或估时。
3. 没有源行证据，不写「已匹配」；最终只允许「已匹配」和「未匹配」。
4. 没有可复算的时效来源，该列填 `--`；禁止用经验值、类比值或无法追到源行的数补齐。
5. 不能用高层模块、依赖模块或相似名称兜底；必须引用命中行原文。
6. P1 / P2 / P3 之间不加系数；一个报价行覆盖多条历史行或原子任务时，三列分别求和。最终不输出「部分匹配」。
7. 标准功能行命中时，直接读取该行「产品」「研发」「交付」时效；三项数据都没有时，三列按 `0`。标准行部分时效缺失时，缺失列填 `--`。
8. 时效单位为人天，保留一位小数；整数可写 `1`、`8`。
9. 命中历史工时清单时，直接读取源行工时；命中多行时三列分别累加，不得改数、取平均或再判断。
10. 匹配前必须先读取 `knowledge-base` 技能，并用知识库工具确认可检索范围、检索标准/历史数据和补充证据；无可用知识库或无命中时如实登记，不得静默跳过。
11. Excel 生成必须使用 `xlsx` 技能：先用 `scripts/fill_quote.py` 固化布局，再用 `xlsx/scripts/recalc.py` 复算公式；未通过不交付。
12. 交付文件必须写入 outputs，并调用 `present_artifacts` 展示。

## 主流程

```text
读取并解析输入 → 登记数据源 → 澄清范围 → 拆需求能力项 → 知识库匹配 → 计算时效 → 绑定依赖模块 → 生成报价单 → xlsx 复算核验 → 展示交付物
```

复制并勾选：

```text
- [ ] 上传附件已全部解析；Office/PDF 已转 Markdown 或表格已按实际行读取
- [ ] 输入足以报价；不足时已调用 `ask_user_question`，未凭空补需求
- [ ] 范围已澄清（或已声明假设）
- [ ] 标准清单、历史清单、需求清单已登记并区分用途
- [ ] 已读取 `knowledge-base` 技能并执行知识库检索；无可用库或无命中已登记
- [ ] 每条需求已拆成能力项；红字、批注等人工语义已转成显式字段
- [ ] 每个匹配结论都有文件、Sheet、行号和原文证据
- [ ] 每行「工时说明」都按 `产品=...；研发=...；交付=...` 逐列写取数式
- [ ] 每个非零工时都能定位到标准行、历史功能行，或拆成有定级原因的 P3 原子任务；无法追溯的列为 `--`
- [ ] 原本部分覆盖的需求已拆成「已匹配」和「未匹配」两行，并设置同一个 `merge_group`
- [ ] 拆分行的 Excel 一级、二级功能已按 `merge_group` 合并
- [ ] 依赖模块已展开且三级功能名带 *
- [ ] Excel 已用 quote 脚本生成，并已用 xlsx 技能完成公式复算
- [ ] 回复只含工时摘要、证据依据、假设与缺口
- [ ] 已调用 `present_artifacts` 展示最终 Excel
```

## 1. 输入门禁与澄清范围

先处理输入，再判断能不能报价：

1. 逐个登记上传附件路径和文件名；存在上传附件时必须全部读取。
2. PDF、DOCX、DOC 和图片先用 `ocr_parse_file` 转成 Markdown，再 `read_file` 解析结果。
3. XLSX、XLS、CSV 表格按 `xlsx` 技能读取实际 Sheet 和数据行；不要用 OCR 预览替代精确行号，尤其是需要作为时效依据的表格。
4. 附件未读、解析失败或路径不可访问时，不得继续估时；要说明失败原因并等待补充。
5. 没有上传附件时，不得凭记忆假设清单；先读取 `knowledge-base` 技能并检索可用的需求、标准或历史数据。
6. 用户输入仍不足以确定需求、范围或数据源时，必须调用 `ask_user_question`；不要用假设替代用户未给的关键能力。

附件和知识库数据可读后，如果模块边界不清或看不出是否标准产品，再追问。一次问清：

- 对标哪个标准产品或标准产品 Sheet
- 本期必做模块、明确不做的模块
- 是否含实施、培训、质保（默认不含，除非用户声明）
- 是否有工期或人天上限（只作披露，不倒挤工时）

信息仍不全时，列出假设后继续，并在最终回复的「假设与缺口」中复述。

## 2. 登记数据源

不要假设固定文件名。每个任务先登记实际数据源：

| 项 | 必填 | 说明 |
| --- | --- | --- |
| 文件名 | 是 | 使用真实文件名 |
| 文件性质 | 是 | 标准清单 / 历史工时清单 / 需求清单 |
| Sheet | 是 | 实际用于匹配的 Sheet |
| 关键字段 | 是 | 功能描述、是否最小销售单元、依赖模块、时效列等 |
| 有效行范围 | 是 | 排除说明行、空行、合计行 |
| 可信度 | 是 | 已确认 / 待确认；历史清单必须确认可作时效依据 |

读取表格时不要只信维度元数据；要按实际数据行解析，并保留行号作为证据。

进入匹配前必须做知识库核查：

1. 先读取 `knowledge-base` 技能，确认每个工具的入参、返回和限制。
2. 调用 `list_kbs` 确认可用知识库，再按需求能力项、标准功能名和历史功能名调用 `query_kb`。
3. 检索片段不足以取得完整表格或行号时，用 `search_file` 找文件，必要时 `download_kb_file` 下载原始文件后按表格解析。
4. 即使已有上传标准或历史清单，也要检索知识库确认是否有补充或更新版本；没有命中时登记「知识库无补充」。
5. 无可用知识库时登记阻塞，不得假装已完成知识库匹配。

## 3. 拆需求能力项

先把用户需求收成最小可交付能力点，再匹配。

报价行字段：

| 字段 | 必填 | 写法 |
| --- | --- | --- |
| 一级功能 | 是 | 最高层模块 |
| 二级功能 | 是 | 一级下的子模块 |
| 三级功能 | 建议 | 用户可感知的最小交付单元 |
| 核心功能描述 | 是 | 「角色 + 动作 + 业务目标」，1–2 句 |

每条报价行继续拆能力项：

| 字段 | 说明 |
| --- | --- |
| 能力项 | 可单独判断的短句 |
| 是否必做 | 必做 / 非必做 |
| 当前状态 | 已有 / 缺失 / 待确认 |
| 判断依据 | 用户说明、源表行、红字转写、批注转写 |

Excel 红色字体和批注只是表现层信息；除非已转成上述字段，否则不能参与业务判定。

粒度：报价行 = 最小销售单元。不要把「用户登录」「密码重置」这类历史原子任务默认拆成独立报价行，除非用户清单本身就是该粒度。

## 4. 逐项匹配

对每条报价行，用「核心功能描述」和能力项矩阵对齐权威数据。匹配键是「角色 + 操作 + 业务对象 + 目标」，禁止只比功能名称。

| 优先级 | 数据层 | 采用条件 | 功能匹配结果 |
| --- | --- | --- | --- |
| P1 | 标准产品最小销售单元 | 必做能力全部可直接复用 | 已匹配；直读标准行时效 |
| 拆分 | 标准或历史只覆盖部分能力 | 覆盖部分和缺口必须分开 | 输出「已匹配」行 + 「未匹配」行 |
| P2 | 历史可比功能或组合 | 完整覆盖该独立能力 | 已匹配；直读或累加历史时效 |
| P3 | AI 评估 | 标准和历史都无可复用单元 | 未匹配 |

判定定义：

- **已匹配**：所有必做能力项都有源行覆盖，主路径无需新增。
- **拆分行**：只有部分能力可复用时，禁止合并成一行；先拆「已匹配」，再拆「未匹配」。
- **未匹配**：找不到可复用源行；不要为了表面完整挂高层模块。

每个结论至少保存一条证据：`文件名 + Sheet + 行号 + 命中原文 + 覆盖/缺口说明`。引用多个源行时，全部列出。

## 5. 计算时效

能力来源和时效来源分开记录。

| 类型 | 允许来源 | 依据要求 |
| --- | --- | --- |
| 标准 | 标准行三列时效 | 文件、Sheet、行号和原始数值；三项都没有时按 0 |
| P2 | 历史可比行 | 文件、Sheet、所有参与行号；单行直读，多行求和 |
| P3 | AI 拆解 | 原子任务表和合计式 |

「工时说明」必须逐列写推导式：`产品=...；研发=...；交付=...`。每个数字都要写出「功能或原子任务」、数值、来源和行号；P3 项必须写 AI评估和定级原因。只写“P2 可复用”“有底座”或“无历史参照”不算工时说明。任一列无法追溯时，该列填 `--`，不得拍数。

## 6. 部分覆盖拆分

标准或历史只覆盖一条需求的部分能力项时，不要输出「部分匹配」，也不要把底座时效和 AI 缺口时效相加到一行。拆成两条相邻报价行：

| 行 | 功能匹配结果 | 时效 |
| --- | --- | --- |
| 被覆盖能力 | 已匹配 | 标准或历史源行直读 |
| 未覆盖缺口 | 未匹配 | P3 原子任务拆解 |

两行的一级、二级功能保持一致，三级功能分别写被覆盖能力和缺口能力；JSON 中两行使用同一个非空 `merge_group`。生成器据此合并这两行的 Excel A、B 列。

## 7. 依赖模块

若命中的最小销售单元在标准清单中有「二级功能依赖模块」或「三级功能依赖模块」，且值不是 `-`、`无`、空：

1. 为每个依赖模块各增一行，紧跟主功能之后。
2. 三级功能名称末尾加 `*`，无空格，例如 `外部平台对接*`。
3. 依赖行时效取该依赖模块作为最小销售单元时的时效；取不到则按 P1 → P2 → P3 降级并写明依据。
4. 依赖行计入总时效。报价单不另设「依赖」列，只靠 `*` 识别。

## 8. 生成报价单

生成前先读取并遵循 `xlsx` 技能的 `SKILL.md`；它的公式复算和表格校验是必选步骤。然后将匹配结果和证据写成 JSON，进入 quote 技能目录后调用：

```bash
uv run scripts/fill_quote.py --input <rows.json> --output <交付文件.xlsx>
```

列顺序固定为 13 列，不要增删：

`一级功能 | 二级功能 | 三级功能 | 核心功能描述 | 产品时效 | 研发时效 | 交付时效 | 时效总计 | 工时说明 | 功能匹配结果 | 匹配模块/功能 | 匹配依据说明 | 匹配来源`

生成和交付必须走 `xlsx` 技能：

1. 用 `scripts/fill_quote.py` 生成固定布局。
2. 用 `xlsx` 技能的 `scripts/recalc.py` 复算公式；`errors_found` 或公式为空时不交付。
3. 最终文件保存到 outputs；前端展示前调用 `present_artifacts`。

来源写实际文件，不写记忆中的项目名：

- 仅标准：`{实际标准文件名}（Sheet：{实际Sheet}，行：{行号}）`
- 仅历史：`{实际历史文件名}（Sheet：{实际Sheet}，行：{行号}）`
- 标准时效 + 历史时效：两个来源用 ` + ` 连接，并逐列写出每个参与源行
- 标准行部分缺失：保留标准来源；缺失列的来源后写 `时效：{列}缺失，按 --`
- P3：`AI评估（原子任务拆解）`
- 来源来自知识库时，同时写知识库名和文件名

## 9. 核验后交付

脚本通过后仍必须核对：

- 每行 `产品时效 + 研发时效 + 交付时效 = 时效总计`
- 每行工时说明是逐列取数式；标准行直读时写出标准功能行和原始值，标准三项缺失为 0 时也写出标准功能行，历史命中是直读或累加式，P3 是原子任务合计式
- 合计行四列分别等于明细之和
- 每个匹配状态都有真实源行证据
- 每个工时都能按依据重算，或已列出 P3 原子任务
- 依赖行三级功能带 `*`
- 已匹配有匹配模块、依据、来源；未匹配时模块为 `-`，依据为「未从标准产品功能清单和历史项目库中找到匹配项」，来源为「AI评估（原子任务拆解）」

任一项不通过，不交付正式报价单。

对话回复只保留三段，不要贴整张表：

1. **工时摘要**：产品 / 研发 / 交付 / 总计，已匹配 / 未匹配行数，拆分行组数，依赖模块行数；存在 `--` 时必须说明缺口
2. **证据依据**：P1 命中的标准行、P2 参与的历史行、P3 原子任务，以及逐列取数式
3. **假设与缺口**：未确认范围、无法追溯为 `--` 的列、无历史参照且不能拆解的行

## 允许的工具

- terminal：执行 `scripts/fill_quote.py` 和 `xlsx` 技能的 `scripts/recalc.py`
- 技能依赖：`xlsx`、`knowledge-base`；Excel 生成必须遵循 `xlsx`，知识库读取和检索必须遵循 `knowledge-base`
- 输入门禁：`ocr_parse_file` 解析 PDF/Office/图片，`read_file` 读取文本和解析结果，`ask_user_question` 补齐关键缺口
- 交付物：`present_artifacts`
- 知识库：`list_kbs`、`query_kb`、`open_kb_document`、`find_kb_document`、`search_file`、`download_kb_file`
- 文件读取：读取用户上传或从知识库下载的标准、历史、需求清单；Office/PDF 先解析为可读内容

## 角色边界

你是报价评估员，不是销售也不是架构师。不确定先问；问不清就写假设。知识库或口头类比只用于说明参照关系，不能用来改写或加成工时。
