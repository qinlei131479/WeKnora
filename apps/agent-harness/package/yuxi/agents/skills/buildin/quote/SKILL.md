# 报价技能书

基于权威数据与报价规则评估工时，按模板导出可追溯报价单。工时只允许来自标准清单固定时效、历史结算时效中位数或标注后的 AI 评估；禁止凭记忆报工时，禁止用平均值冒充类比。

权威数据不在本技能目录内：

- 标准产品、历史项目：由用户在对话中提供文件，或通过知识库检索（`list_kbs` / `query_kb` / `open_kb_document` / `download_kb_file`）
- 输出模板与填写规则：`references/output-spec.md`
- 匹配与时效规则：`references/matching.md`
- 权威数据结构索引：`references/data-index.md`
- P3 拆解估时：`references/ai-estimation.md`

细则按需读取，不要预加载。

## 硬约束

1. 本阶段只输出工时。不要写单价、税率、金额、含税金额。
2. P1 / P2 / P3 之间不加任何乘数系数，直接取原始时效。
3. 项目总时效 = Σ(最小销售单元时效 + 其绑定依赖模块时效)。
4. 禁止编造工时。标准清单该行时效为空时，按 `references/matching.md` 降级，并在匹配依据里写清时效来源。
5. 匹配不到必须暴露缺口：功能匹配结果写「未匹配」，匹配来源写「AI评估」，不得用项目总均值或拍脑袋整数冒充类比。
6. 时效单位为人天。保留一位小数（如 `0.5`、`5.5`）；整数可写 `1`、`8`。
7. 用 `scripts/fill_quote.py` 生成报价单，不要手改单元格布局。

## 主流程

```
澄清范围 → 拆 D0 需求清单 → 逐项 P1/P2/P3 匹配 → 绑定依赖模块 → 填报价单 → 校验合计 → 交付摘要
```

复制并勾选：

```
- [ ] 范围已澄清（或已声明假设）
- [ ] D0 需求功能清单已拆完
- [ ] 每一行完成匹配并标注来源
- [ ] 依赖模块已展开且三级功能名带 *
- [ ] Excel 已用脚本生成且合计校验通过
- [ ] 回复只含工时摘要、类比依据、假设与缺口
```

### 1. 澄清范围

需求只有一句话、模块边界不清、或看不出是否标准产品时，先追问再估时。一次问清：

- 是否对标标准产品：数智全链运营 / 智慧行业 / 焊点检测 / 非标准定制
- 本期必做模块、明确不做的模块
- 是否含实施、培训、质保（默认不含，除非用户声明）
- 是否有工期或人天上限（只作披露，不倒挤工时）

信息仍不全时，列出假设后继续，并在最终回复的「假设与缺口」中复述。

### 2. 拆 D0 需求功能清单

先把用户需求收成最小可交付功能点，再匹配。字段：

| 字段 | 必填 | 写法 |
| --- | --- | --- |
| 一级功能 | 是 | 最高层模块，如「监测配置与管理」 |
| 二级功能 | 是 | 一级下的子模块 |
| 三级功能 | 建议 | 用户可感知的最小交付单元 |
| 核心功能描述 | 是 | 「角色 + 动作 + 业务目标」，1–2 句 |

粒度：报价行 = 最小销售单元，不要把历史原子任务（如「用户登录」「密码重置」）默认拆成独立报价行，除非用户清单本身就是该粒度。

### 3. 逐项匹配（P1 → P2 → P3）

对 D0 每一行，用「核心功能描述」对齐权威数据，**禁止只比功能名称**：

| 优先级 | 检索层 | 何时采用 | 时效 | 功能匹配结果 |
| --- | --- | --- | --- | --- |
| P1 | 标准产品最小销售单元 | 核心能力可直接复用 | 标准清单该单元固定时效 | **已匹配** |
| P1 部分 | 标准产品最小销售单元 | 主体可复用，但缺接口/场景/规则 | 标准时效 + 缺口走 P2/P3，**分项相加且不乘系数** | **部分匹配** |
| P2 | 历史项目功能点或组合 | 标准清单无该单元，但历史有相似组合 | 历史「产品/研发/交付」中位数；组合则取组合合计 | **部分匹配**（高度复用且几乎不改也可 **已匹配**） |
| P3 | AI 评估 | 标准与历史都无匹配 | 按 `references/ai-estimation.md` 拆原子任务累加 | **未匹配** |

判定操作定义：

- **已匹配**：标准或历史已覆盖该操作与业务目标，可直接复用界面/模型/流程，无需新增主路径。
- **部分匹配**：有相似底座，但缺对象、接口、场景或规则，必须写清「已有什么 / 缺什么 / 要改什么」。
- **未匹配**：两库都找不到可复用单元。模板用「未匹配」，不要写规则原文里的「不匹配」。

匹配字段写法必须以 `references/output-spec.md` 的模拟金样为准。

### 4. 依赖模块

若命中的最小销售单元在标准清单中有「二级功能依赖模块」或「三级功能依赖模块」（值不是 `-` / `无` / 空）：

1. 为每个依赖模块各增一行，紧跟主功能之后。
2. 三级功能名称末尾加 `*`，无空格，例如 `多AI平台对接*`。
3. 依赖行时效从标准清单取该依赖模块作为最小销售单元时的时效；取不到则按第 3 步降级，并在依据中说明。
4. 依赖行计入总时效。报价单不另设「依赖」列，只靠 `*` 识别。

### 5. 生成报价单

将匹配结果写成 JSON，进入技能目录后调用：

```bash
uv run scripts/fill_quote.py --input <rows.json> --output <交付文件.xlsx>
```

列顺序必须与模板一致（12 列，不要增删）：

`一级功能 | 二级功能 | 三级功能 | 核心功能描述 | 产品时效 | 研发时效 | 交付时效 | 时效总计 | 功能匹配结果 | 匹配模块/功能 | 匹配依据说明 | 匹配来源`

填写要点（金样见 `references/output-spec.md`）：

- 每一数据行都写一级/二级/三级，不要沿用标准清单的合并空白。
- `时效总计`、合计行用公式，不要手算硬编码。
- 合计行：`A:D` 合并，A 列写「合计」，E–H 为各列 SUM；I–L 留空。
- 不要把未匹配字段范例原样抄进交付文件。
- 匹配模块：`{一级功能} > {被复用的最小销售单元}`，例如 `CMS媒资管理系统 > CP/SP管理`。
- 匹配来源：
  - 仅标准：写出实际命中的标准清单文件名与 Sheet，例如 `标准化产品功能清单.xlsx（Sheet：数智全链运营）`
  - 标准+历史：`{标准文件名} + {历史文件名}`
  - 仅历史：历史文件名
  - P3：`AI评估`
  - 来源是知识库文档时，同时写清知识库名与文件名

### 6. 校验后交付

脚本通过后仍须人工核对：

- 每行 `产品时效 + 研发时效 + 交付时效 = 时效总计`
- 合计行四列分别等于明细之和
- 依赖行三级功能带 `*`
- 已匹配 / 部分匹配必填匹配模块、依据、来源；未匹配时匹配模块为 `-`，依据为「未从标准产品功能清单和历史项目库中找到匹配项」，来源为「AI评估」

对话回复只保留三段，不要在聊天里贴整张表：

1. **工时摘要**：产品 / 研发 / 交付 / 总计（人天），已匹配 / 部分匹配 / 未匹配行数，依赖模块行数
2. **类比依据**：P1 命中的标准单元、P2 参照的历史项目与是否取中位数/组合合计
3. **假设与缺口**：未确认范围、标准清单时效空缺、无历史参照的 P3 行

## 允许的工具

- terminal：执行 `scripts/fill_quote.py`
- 知识库：`list_kbs`、`query_kb`、`open_kb_document`、`find_kb_document`、`search_file`、`download_kb_file`
- 文件读取：读取用户上传或下载到沙盒的标准/历史清单

## 角色边界

你是报价评估员，不是销售也不是架构师。不确定先问；问不清就写假设。知识库或口头类比只用于「为何参照该项目」，不能用来改写或加成工时。
