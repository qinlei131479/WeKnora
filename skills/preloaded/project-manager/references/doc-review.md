# 项目文件检查与优化建议（Document Review）

用于对项目经理提供的项目文件（项目章程、WBS、进度计划、风险登记册、干系人登记册、沟通计划、周报、会议纪要、变更请求、复盘报告等）进行检查、挑问题并给出优化建议。检查结论必须能指到文件具体位置，建议必须落到具体修改。

## 一、检查流程（五步）

1. **读全**：完整读取文件，先判断文件类型与用途（是章程？是周报？用于什么决策/汇报）。
2. **建清单**：按文件类型选定检查维度与检查要点（见"三"），形成该文件的检查清单。
3. **逐项核查**：逐字段/逐行过一遍，记录"位置 + 问题 + 证据"（证据引用原文，不改写）。
4. **分级**：按严重度给每条问题定级（阻断/高/中/低）。
5. **输出**：输出问题清单表 + 优化建议；对高价值问题给出"修改后示例"。

## 二、六大检查维度

| 维度 | 检查什么 | 典型问题信号 |
|---|---|---|
| 完整性 | 必填字段/章节是否齐全，有无空占位 | "/"、"TBD"、"？"、留空、"待定" |
| 一致性 | 跨章节/跨文件口径是否统一 | 同一预算两处不同、名称写错、日期矛盾、负责人不一致 |
| 可操作性 | 任务是否可执行可验收 | 行动项无负责人/无截止时间/无验收标准 |
| 质量标准 | 是否符合方法论文档规范 | 目标非 SMART、WBS 违反 100% 原则、估算无依据、无版本号 |
| 合规性 | 是否满足组织流程/合同/验收要求 | 缺审批签字、缺确认时间、缺归档材料、无审计字段 |
| 可追溯性 | 决策/变更/问题是否可回溯 | 变更无记录、决策无依据、无创建人/时间/更新人 |

## 三、按文件类型的检查要点

### 1. 项目章程（启动）
- 目标是否 **SMART**（具体/可衡量/可达成/相关/有时限）？
- 范围是否明确（做什么 + 不做什么）？
- 发起人授权、主要干系人、里程碑时间表、总体预算是否齐全？
- 主要风险与假设是否列出？成功标准是否可衡量？
- 是否有版本/批准信息（起草人、审批人、日期）？

### 2. WBS（范围）
- 是否面向**交付物**而非动作？
- 是否满足 **100% 原则**（下层之和 = 上层，不遗漏不重复）？
- 最底层是否为可估算、可分配、可验收的**工作包**？
- 编码是否统一（如 1、1.1、1.1.1）？是否混入了时间顺序或依赖关系（WBS 不应含）？

### 3. 进度计划（规划）
- 是否有明确里程碑与关键路径？
- 任务间依赖关系（FS/SS/FF）是否标明？
- 每项任务是否有负责人与计划/实际分开的记录列？
- 是否有多版本变更？是否有版本号与变更说明（防止"只留最后版本"）？
- 估算是否有依据（历史数据/三点估算）？工期是否合理（如 <1 天的任务过碎）？

### 4. 风险登记册（监控）
- 概率/影响/得分是否齐全且有规则（如 概率×影响）？
- 是否有应对策略（规避/转移/减轻/接受）与责任人？
- 是否有触发条件？状态是否持续更新（未只停留在识别日）？
- 高评分风险是否有明确的"下一步行动"？

### 5. 干系人登记册
- 是否覆盖全部受影响/影响项目的人（含容易被漏的：监管、内部支持团队）？
- 是否有权力-利益分级与参与策略（重点管理/令其满意/随时告知/监督）？
- 知情级别与联系方式是否可查？

### 6. 沟通计划
- 沟通事项/受众/频率/渠道/负责人是否一一对应？
- 是否覆盖关键干系人的信息需求？频率与渠道是否现实（过多会失效）？

### 7. 进度周报
- "本期完成/下期计划"是否有据（对应计划条目）？
- 风险与问题是否持续跟踪（同一条风险是否连续出现却不更新状态）？
- 偏差与预测是否量化（如 SPI/CPI、延期天数）？
- 是否有"需干系人决策事项"清单？

### 8. 会议纪要
- 时间/地点/参会人是否完整？
- 议题→结论是否对应？行动项是否有"事项-负责人-截止时间"？
- 待确认事项是否单独列出并跟踪？

### 9. 变更请求
- 变更描述/理由/影响评估（范围-进度-成本-质量）是否完整？
- 是否有方案选项、申请人、审批状态？是否走 CCB 审批？
- 变更是否反写回计划基线（不更新基线 = 变更白提）？

### 10. 项目复盘报告
- 项目结果 vs 目标是否有**数据**支撑（不是定性描述）？
- 做得好/做得差是否具体可复用/可避免？
- 延期/超支原因是否追溯到根因？改进措施是否可执行且有责任人？
- 是否沉淀到经验教训登记册/组织知识库？

## 四、严重度分级

| 级别 | 含义 | 处理要求 |
|---|---|---|
| 阻断 | 影响项目决策/验收/合规，必须修改 | 立即改，否则决策或验收受阻 |
| 高 | 影响执行或追溯，建议修改 | 优先处理（如里程碑缺失、数据矛盾） |
| 中 | 影响效率/复用/质量观感 | 择机优化（如占位符、字段冗余） |
| 低 | 格式/表述类 | 锦上添花（如措辞、排版） |

## 五、输出结构（模板）

```
## 检查结论（先说结论）
- 文件类型 / 用途 / 总体评价（可用/需修改后可用/不可用）+ 问题总数与分级统计

## 问题清单
| 序号 | 位置 | 问题 | 证据（原文引用） | 严重度 | 改进建议 |

## 重点优化建议（Top 3）
- 每条：问题 → 影响 → 具体改法 → 修改后示例

## 检查范围与限制
- 检查覆盖范围（哪些字段/章节）、未覆盖项、依据标准（PMBOK/组织规范/最佳实践）
```

## 六、质量要求（强制）

1. 每条问题必须能指到文件**具体位置**（章节/行/字段/单元格），不泛泛而谈。
2. 证据**引用原文**，不转述改写；原文缺失处标注"原文无此项"。
3. 建议必须落到**具体修改**（改哪个字段、怎么改、改成什么），必要时给修改后示例。
4. 区分"标准要求"（PMBOK/组织流程规定）与"最佳实践"（业界常见做法），不混为一谈。
5. 涉及数字的检查（预算、工期、EVM）必须可复现，不凭印象判断"对错"。
6. 检查结论不超出文件实际内容；文件里没有的信息不得脑补。
7. 若文件缺失过程类资料（会议记录、变更历史、版本快照），在"完整性/可追溯性"中明确指出并给出补录建议。
